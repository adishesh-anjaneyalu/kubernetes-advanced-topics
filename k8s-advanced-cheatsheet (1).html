NetworkPolicy
Firewall between pods — control who can talk to who
networking.k8s.io/v1
🤔
Why NetworkPolicy Exists
Without it every pod can reach every other pod
The Problem: By default Kubernetes has no firewall between pods. A hacked frontend pod can directly attack your database on port 5432. That is a serious security risk in production.
WITHOUT NetworkPolicy — dangerous: frontend ──→ postgres ✅ allowed (should be blocked!) any pod ──→ any pod ✅ allowed (very dangerous!) WITH NetworkPolicy — safe: frontend ──→ backend ✅ allowed frontend ──→ postgres ❌ BLOCKED backend ──→ postgres ✅ allowed internet ──→ postgres ❌ BLOCKED
⚠️ Needs a CNI that supports NetworkPolicy — use Calico or Cilium on EKS
💡 AWS VPC CNI now supports NetworkPolicy from EKS 1.25+ with addon enabled
🏗️
NetworkPolicy Structure
podSelector + ingress + egress rules
How it works: Pick which pods this policy applies to using podSelector. Then define what traffic is allowed IN (ingress) and OUT (egress). Everything not explicitly allowed is blocked.
networkpolicy.yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: protect-postgres
  namespace: production
spec:
  podSelector:          # which pods this applies to
    matchLabels:
      app: postgres
  policyTypes:
    - Ingress              # control who can send TO postgres
    - Egress               # control where postgres can send
  ingress:               # allowed incoming connections
    - from:
        - podSelector:
            matchLabels:
              app: backend # ONLY backend allowed
      ports:
        - port: 5432
🚫
Step 1 — Deny All First (Best Practice)
Zero-trust: block everything, then allow only what's needed
Production Rule: Always apply deny-all FIRST in every namespace. Then add specific allow policies. This is called zero-trust networking — the industry standard.
deny-all.yamlapply this FIRST
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: deny-all
  namespace: production
spec:
  podSelector: {}        # {} = applies to ALL pods
  policyTypes:
    - Ingress
    - Egress
  # No ingress/egress rules = EVERYTHING blocked!
⚠️ After deny-all pods lose connectivity! Apply your allow policies immediately after or do it in the same kubectl apply.
✅
Step 2 — Allow Specific Traffic
One policy per connection you need
allow-backend-to-postgres.yaml
spec:
  podSelector:
    matchLabels:
      app: postgres         # protects postgres pods
  policyTypes: [Ingress]
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: backend   # only backend can connect
      ports:
        - port: 5432
allow-monitoring.yaml
# Allow Prometheus from monitoring namespace
spec:
  podSelector: {}          # all pods
  policyTypes: [Ingress]
  ingress:
    - from:
        - namespaceSelector: # from another namespace!
            matchLabels:
              name: monitoring
      ports:
        - port: 9090
🌍 Use namespaceSelector for traffic from pods in other namespaces like monitoring
🔑 Pod labels in Deployment must match the podSelector in NetworkPolicy

KEDA — Kubernetes Event Driven Autoscaler
Scale on real events — SQS, Kafka, Cron, HTTP — and scale to ZERO to save cost
keda.sh/v1alpha1
⚖️
HPA vs KEDA
Why KEDA is more powerful in production
HPA only watches CPU/memory — reactive and slow. KEDA watches real workload events and can scale to zero pods saving huge cost when idle!

KEDA with AWS SQS — Full Example
Scale workers based on SQS queue message count
How KEDA + SQS works: [SQS Queue] ← KEDA checks every 30s 0 messages → 0 worker pods (saves cost!) 100 messages → 10 worker pods 500 messages → 20 worker pods (max) 0 messages → back to 0 pods after cooldown
keda-sqs.yamlmost common in production
# TriggerAuthentication — how KEDA connects to AWS
apiVersion: keda.sh/v1alpha1
kind: TriggerAuthentication
metadata:
  name: aws-trigger-auth
  namespace: production
spec:
  podIdentity:
    provider: aws-eks         # uses IRSA — no keys needed!
---
# ScaledObject — the main config
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: worker-scaledobject
  namespace: production
spec:
  scaleTargetRef:
    name: worker-deployment    # your Deployment name
  minReplicaCount: 0           # scale to ZERO when idle!
  maxReplicaCount: 20
  pollingInterval: 30          # check every 30 seconds
  cooldownPeriod: 300          # wait 5min before scaling down
  triggers:
    - type: aws-sqs-queue
      authenticationRef:
        name: aws-trigger-auth
      metadata:
        queueURL: https://sqs.ap-south-1.amazonaws.com/283904064984/orders-queue
        queueLength: "10"      # 1 pod per 10 messages
        awsRegion: ap-south-1

AWS Secrets Manager + External Secrets Operator
Fetch secrets from AWS automatically — no passwords ever in Git!
external-secrets.io/v1beta1
🤔
The Problem With Normal K8s Secrets
base64 is NOT encryption — anyone can decode it
Big Problem: Kubernetes Secrets are just base64 encoded — NOT encrypted. If your YAML gets into Git, anyone can decode the password in seconds.
BAD WAY — what beginners do: secret.yaml → pushed to Git → password visible! base64 decode → plain text password — anyone can see! GOOD WAY — production standard: Password stored in AWS Secrets Manager (encrypted) ↓ External Secrets Operator fetches automatically ↓ Kubernetes Secret created inside cluster only ↓ Pod uses it as env var Zero passwords in Git. Ever.
⚙️
How It Works — 3 Resources
SecretStore + ExternalSecret = automatic K8s Secret
You write 2 resources:
1. SecretStore — connects to AWS Secrets Manager (once per namespace)
2. ExternalSecret — which AWS secret to fetch, creates K8s Secret automatically
[AWS Secrets Manager] stores: /prod/myapp/secrets = DB_PASSWORD, JWT_SECRET [SecretStore] tells ESO: use ap-south-1 + this IAM role [ExternalSecret] says: fetch /prod/myapp/secrets every 1 hour [ESO Operator] creates automatically: [K8s Secret: myapp-secret] ← auto-managed! injected into pod as: DB_PASSWORD=supersecret JWT_SECRET=myjwt ✅
📦
Step 1 — Install ESO + Create AWS Secret
Install External Secrets Operator via Helm
terminal — install ESO
helm repo add external-secrets \
  https://charts.external-secrets.io
helm repo update

helm install external-secrets \
  external-secrets/external-secrets \
  --namespace external-secrets \
  --create-namespace

# Verify:
kubectl get pods -n external-secrets
external-secrets-xxx   Running ✅
terminal — store secret in AWS first
aws secretsmanager create-secret \
  --name /prod/myapp/secrets \
  --secret-string '{"DB_PASSWORD":"supersecret","JWT_SECRET":"myjwt"}' \
  --region ap-south-1
💡 ESO needs IAM permission. Attach SecretsManagerReadWrite policy via IRSA to the ESO service account.
🔗
Step 2 — SecretStore
Connect ESO to your AWS account — once per namespace
SecretStore is your connection config to AWS. Create one per namespace. Use IRSA in production — never hardcode AWS access keys!
secretstore.yamlone per namespace
apiVersion: external-secrets.io/v1beta1
kind: SecretStore
metadata:
  name: aws-secretstore
  namespace: production
spec:
  provider:
    aws:
      service: SecretsManager
      region: ap-south-1
      auth:
        jwt:                     # IRSA — no access keys!
          serviceAccountRef:
            name: external-secrets-sa
---
# OR ClusterSecretStore for all namespaces at once:
kind: ClusterSecretStore      # no namespace field needed!
metadata:
  name: aws-cluster-secretstore
📥
Step 3 — ExternalSecret (Fetch + Create K8s Secret)
One ExternalSecret per app — ESO manages the rest automatically
externalsecret.yamlone per app
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: myapp-external-secret
  namespace: production
spec:
  refreshInterval: 1h           # re-sync every hour
  secretStoreRef:
    name: aws-secretstore         # must match SecretStore!
    kind: SecretStore
  target:
    name: myapp-secret            # K8s Secret name to create
    creationPolicy: Owner        # ESO owns this secret
  data:
    - secretKey: DB_PASSWORD     # key in K8s Secret
      remoteRef:
        key: /prod/myapp/secrets   # AWS secret name
        property: DB_PASSWORD     # JSON field in AWS secret
    - secretKey: JWT_SECRET
      remoteRef:
        key: /prod/myapp/secrets
        property: JWT_SECRET
deployment-using-eso-secret.yaml
# Use auto-created secret EXACTLY like normal!
spec:
  template:
    spec:
      containers:
        - name: myapp
          image: myapp:1.0.0
          envFrom:
            - secretRef:
                name: myapp-secret # created by ESO!
terminal — verify sync
kubectl get externalsecret -n production
# Should show:
myapp-external-secret  SecretSynced  True  1h

kubectl get secret myapp-secret -n production
# K8s Secret auto-created by ESO ✅
🔄 ESO auto-rotates: update password in AWS → K8s Secret updates on next refresh cycle
🔑 secretKey = name in K8s Secret · property = JSON field in AWS secret
🏭 This is the industry standard for secrets in EKS production — your Shivam Hospital project should use this!
